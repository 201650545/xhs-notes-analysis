2. apply_verdict.py 的判决合法性检查还有缺口

这是本次代码审查中最值得先修复的一处。

当前代码会从判决文件提取 keep、drop，把不在当前批次的 ID 过滤出来，记录为 stray；已有批次标记检查、三件齐全检查以及 dry-run 机制，但没有看到把 stray 一律视为执行失败，也没有看到 keep 与 drop 之间的互斥检查。
GitHub
+1

这意味着异常判决数据可能只产生警告，或者同一笔记落入互相矛盾的操作集合。

必须增加以下执行条件：

Python
Run
keep = verdict["keep"]
drop = verdict["drop"]
known = set(batch.keys())

if len(keep) != len(set(keep)):
    raise ValueError("keep 中有重复 ID")

if len(drop) != len(set(drop)):
    raise ValueError("drop 中有重复 ID")

if set(keep) & set(drop):
    raise ValueError("同一笔记同时判留和判删")

if (set(keep) | set(drop)) - known:
    raise ValueError("判决包含批次外 ID")

在这四项检查通过前，不允许执行任何实际删除。

另外建议将 dry-run 输出的判决文件哈希绑定到正式执行指令，防止预览之后数据被修改，但实际执行仍按旧的人工批准继续运行。

3. 四处同步删除还不是可恢复事务

目前代码采用飞书先删、本地后删的策略。这个顺序能避免飞书删除失败后本地数据先消失，但仍存在两个问题：

飞书多批删除时，如果部分成功、后续失败，本地仍保留全部记录；重新执行会面对已经删除的云端行。

云端删除成功后，本地还要继续修改精选 Markdown、案例文件、分析全文、路由台账、飞书映射。进程在任一步中断，可能留下不一致状态。
GitHub
+1

PREPARED
  ↓
APPROVED
  ↓
REMOTE_APPLIED
  ↓
LOCAL_APPLIED

3. 用已有的 50 篇人工校准样本构建回归测试

最重要的指标是：

误删率：人类最终要留，系统却建议删。

误留率：人类最终要删，系统却建议留。

冲突率：两个模型意见不一致的比例。

人工节省率：原本需要审的篇数中，有多少不再需要逐篇阅读。

七、还值得防范的三项风险

第一，AI 幻觉和来源混淆。 提示词有来源分区还不够，涉及财经、心理健康、教育等事实性主张时，应在方法卡里保留证据状态。笔记正文和外部网页也必须作为不可信数据处理，不能允许其中的文字改变 Agent 的指令或触发删除行为。

第二，公开知识索引的隐私和版权。 即使 b_answers/ 没有上传，公开精选索引仍可能包含实际笔记 ID、来源链接与个人偏好。建议公开仓库只保留脱敏案例和合成示例；第三方内容不应因进入你的知识管线而默认公开。

第三，浏览器自动化对平台实现的依赖。 现有方案复用登录浏览器和页面内部结构，虽然减少了重新登录的操作，但也会受到页面改版、接口变化、平台使用规则和账号风控影响。应让失败自动停止，并优先采用平台允许的访问方式，不以提高频率来解决吞吐问题。

最终结论

如果只允许我选一个最值得做的工程优化，那就是：

建立统一的笔记身份和状态模型，再为所有会改变数据的操作增加校验、授权、日志与恢复能力。

如果只允许我选一个最值得做的知识管理优化，那就是：

把「为什么值得留」延伸到「准备怎么用、实际用了没有、效果如何」。

这两项会让系统从目前能够自动运行的个人项目，变成未来可以持续演化、可信赖且能够反向支持教学与内容创作的知识基础设施。

需要说明审查边界：以上代码问题来自公开仓库的静态阅读，并未在你的本地环境中执行。534 篇分析全文、私有台账和运行日志尚未实际核对；涉及真实数量、吞吐表现和具体数据一致性的判断，仍需要用本地审计脚本验证。
